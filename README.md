# 徽知 · Huizhou Culture Explorer

> 徽州文化知识图谱与 AI 智能问答平台 —— 生成式 AI 与智能体开发课程设计项目

徽知把徽州文化整理成**结构化、可核查、可交互**的知识：你可以浏览文化实体、按关键词与分类检索、
在交互式知识图谱中查看实体之间真实的数据关系，并基于资料向 AI 提问，获得**带来源引用**的回答。
此外，平台还提供一条**可追踪的智能体工作流**——从问题解析、资料检索、依据资料作答，
到引用自我核查与输出归档，六步全部留痕，失败时会明确指出停在哪一步。

## 知识图谱

图谱由 `data/*.json` 实时构建，**不使用任何预生成的图数据**：

| 指标 | 值 |
|---|---|
| 节点 / 边 | 96 / 180（与数据完全一致） |
| 图类型 | `MultiDiGraph`（同向平行边不会被合并） |
| 连通分量 | 1（全部实体同属一个关联网络） |
| 网络直径 | 6 |
| 平均最短关联距离 | 2.939 |
| 文化聚类 | 8 组（模块度优化，探索性分析） |

「知识图谱」页提供：按分类 / 关系类型筛选、聚焦单个实体的关联子图（半径 1–3）、
悬停查看简介、点击节点高亮邻居、任意两实体的最短关联线路查询、
度数 / 介数中心性排名，以及文化聚类浏览。

图谱渲染**完全离线自洽**：`vis-network` 的 JS/CSS 内联进 HTML，
并会清洗 PyVis 模板自带的外部 Bootstrap 引用（详见 `docs/DEVELOPMENT.md` 第 2.3 节）。

生成验证报告，或导出一份可独立打开的交互式图谱：

```bat
python scripts/graph_report.py
python scripts/graph_report.py --path xidi chengzhitang
python scripts/graph_report.py --export outputs/huizhou-knowledge-graph.html
```

导出的 HTML 为单文件（约 830 KB），直接双击用浏览器打开即可拖拽、缩放与点选，
不依赖服务器与网络。

## 文化百科与实体详情

**文化百科页**（`src/ui/pages/explore.py`）

- 关键词检索：覆盖名称、别名、摘要、正文与结构化属性，按字段加权；
  多关键词时「全部命中」优先，并在卡片上标出命中的字段。
- 分类筛选：11 个分类快捷按钮，每个按钮上的数字都是该分类的真实实体数。
- 排序与分页：默认顺序 / 按名称 / 按关联关系数，每页 12 个实体。
- 无结果时显示空状态并说明检索范围，**不会用虚构条目填充**。

**实体详情页**（`src/ui/pages/detail.py`）

- 结构化属性（全部来自 `data/entities.json`）、正文、别名与分类（配色与图谱一致）。
- **关联关系按方向分组**：「从本实体出发」用 `→`、「指向本实体」用 `←`，
  反向关系会使用关系类型登记的反向名称（如 `位于` ↔ `辖有`），绝不把方向说反。
- 参考资料区列出实体来源与关联关系引用的来源，均带**可点击的原文地址**。
- 「在图谱中查看」按钮会把知识图谱页**真实聚焦**到该实体（不是只跳过去）。
- 实体不存在时显示明确的错误状态并提供返回入口，不静默回退到别的实体。

**关于图片**：详情页在实体有图时展示配图并自动附带作者、许可与来源页面；
没有图片时**不显示任何占位图**，页面以纯排版呈现。
图片抓取脚本（`scripts/fetch_images.py`）只接受同时满足三条的图片：自由授权
（CC0 / CC BY / CC BY-SA / 公有领域 / GFDL）、**与实体确实相关**、**Commons 上登记了作者**。
相关性把关是「必含词 + 排除词」两段式的，对「徽州牌坊」「徽州祠堂」这类**带地域的建筑类型名**
还会额外要求出现徽州一府六县的地名——因为曾经真的下错过：同名异地（无锡惠山祠堂）、
同物异指（白云寺院门）都被挡住了。

本机对 Wikimedia 存在 **SNI 域名级阻断**（`commons`/`upload` 的 DNS 被污染、TCP 握手超时，
而 `dumps.wikimedia.org` 正常），因此脚本改经一组**免费中转池**（Microlink / allorigins /
cors.lol / codetabs，带冷却退避与轮换）取回元数据，由 `wsrv.nl` 取回图片字节。
当前已收录 **15 张**真实图片（西递、呈坎、唐模、棠樾、许村、渔梁、承志堂、屯溪、许国石坊、
黄山、齐云山、南屏、徽派建筑、徽州民居、胡庆余堂），全部通过许可白名单校验并逐条署名；
图注由人工对照实际图片内容写定。另有 14 个实体因「找不到真正相关且作者明确的自由授权图片」
而不放图——这一条如实登记在 `assets/images/CREDITS.md` 的「未取得图片的实体」一节。
详见 `assets/images/README.md`。

## AI 智能问答

**回答必须基于检索到的资料**，这是整个模块的设计前提。

**第一步：检索**（`src/qa/retriever.py`）

- jieba 中文分词 + 停用词过滤，查询串额外补充「整串」与「按标点切分的片段」两路，
  避免分词把「徽州三雕」这类专名切碎后漏召回。
- 打分 = **Okapi BM25**（k1=1.5，b=0.75）+ 精确命中加成：
  标题完全等于查询词时加成最高，否则「徽州」这类被近百个实体复用的词
  会让「徽州婚俗」与「徽州」本身得分几乎并列。
- 每份资料的正文里**包含关系叙述**（按关系读法分组成「位于：黟县」「包含组成：歙县、休宁…」），
  因此「宏村属于哪个县」这类问题检索得到答案，而不只是命中实体简介。
- 每条结果都带该实体的登记来源；没有来源的内容不进索引。检索不到就返回空列表，不凑数。

**第二步：作答**（`src/qa/prompt.py` + `src/qa/engine.py`）

资料按 `[1] [2] [3]` 编号后交给后端，系统提示词明确要求：只能使用给定资料、
每个事实后必须标注编号、资料不足时必须直接说明、与徽州文化无关时直接拒答。

后端按 **Dify → OpenAI 兼容大模型 → 本地检索式** 依次尝试，任一层不可用或失败即自动降级。

| 后端 | 触发条件 | 备注 |
|---|---|---|
| Dify 知识库 / 工作流 | 配置了 `DIFY_BASE_URL` + `DIFY_API_KEY` | 支持 chat / agent / workflow 三种应用类型 |
| OpenAI 兼容大模型 | 配置了 `LLM_BASE_URL` + `LLM_API_KEY` + `LLM_MODEL` | 已实测 DeepSeek（`deepseek-chat`）可用 |
| 本地检索式 | **始终可用**（零依赖、可离线） | 直接呈现资料原文，不做生成式改写 |

**第三步：溯源**

- 解析回答里的 `[n]` 编号并与资料表比对，「引用来源」区只列出**真正被引用到**的资料。
- 模型若引用了**不存在的编号**，会被渲染成划掉的红色徽标并在页面上明确提示，而不是被悄悄忽略。
- 未被引用的资料同样列出（标注「未被回答引用」），便于核查检索质量。
- 降级原因（哪个后端被跳过、为什么）**原样显示在页面上**，不让用户误以为用的是最好的那条链路。

```
实测：问「徽商是什么？」→ 检索 5 条资料 → DeepSeek 作答 2.1 s →
      回答中 5 处引用全部可点击核查，grounded = True
```

**为什么强调「不编造」**：本地检索式后端在检索不到时直接回答「没有检索到相关内容」；
大模型后端在遇到无关问题时实测会回复「本次检索到的资料与问题无关，无法回答」。
两条路径都不允许用模型记忆补全数据集中没有的内容。

## 可追踪智能体工作流

在「关于项目」页可以**现场运行**一条六步工作流（`src/agent/workflow.py`），
每一步都留下输入、输出、耗时与状态：

| 步骤 | 做什么 | 中止条件 |
|---|---|---|
| 1 问题解析与实体锚定 | 启发式判断提问类型；把问题里的实体名与别名锚定出来（长词优先，避免「徽州三雕」被「徽州」抢走） | 问题不合法 |
| 2 资料检索 | 放宽条件检索后把锚定实体提到首位；锚定实体没露面时按名字补查一次 | 检索结果为空 |
| 3 依据资料作答 | 走与 AI 问答页**同一条**后端降级链（`QAEngine.answer_from`） | 所有后端不可用 |
| 4 引用自我核查 | 6 项结构化核查，输出「通过 / 警告 / 未通过」分级结论 | 不中止，问题如实上报 |
| 5 纠正重试 | 核查未通过时，带着具体缺陷（缺编号 / 编号不存在）再问一次，**至多一次** | 不中止，失败保留原答案 |
| 6 输出与归档 | 汇总答案、引用、核查结论与完整步骤日志 | — |

**核查不用模型自评**，全部是程序可判定的硬条件：回答非空、有来源编号、编号真实存在、
每条引用都能落到登记来源、检索资料利用率 ≥ 50%（警告级）、未发生后端降级（警告级）。
因此结论可复现、可测试，也不会被「我觉得没问题」糊弄过去。

**整体状态分四种**，过程信息不被抹平：

| 状态 | 含义 |
|---|---|
| 已按预期完成 | 全部步骤干净，核查一次通过 |
| 经自我纠正后完成 | 中途触发过纠正且最终核查通过 |
| 完成但存在问题 | 核查未通过，或存在警告步骤（如后端降级、未锚定到实体） |
| 中途中止 | 问题不合法 / 检索不到资料 / 后端全挂，余下步骤记为「跳过」并写明原因 |

```
实测（本地检索式后端）：
问「宏村是什么？」        → 5 步执行（纠正被跳过）→ 检索 5 条 → 引用 5 处
                            核查 6/6 通过 → 状态「已按预期完成」
问「宏村和西递有什么关系」  → 提问类型「关系类」，锚定实体「宏村、西递」
问「量子纠缠与超导体」      → 第 2 步中止，余下 4 步全部「跳过」，未生成任何回答
```

工作流与问答页共用同一条作答链路，区别只在于工作流把「检索」与「作答」当成两个可分别计时、
可分别检查的步骤——不会出现「同一个问题在两个页面上答案不一致」的情况。

## 质量评估

「功能能跑」和「效果好不好」是两件事。这一层用**人工标注集**回答后者，
并且做到可复现、可核对——不是挑几个好例子演示，也不是拿检索结果反推标准。

```bat
python scripts/evaluate.py                 :: 检索 + 问答，离线
python scripts/evaluate.py --verbose       :: 附未命中与误召回明细
python scripts/evaluate.py --json outputs/eval.json
python scripts/evaluate.py --live          :: 换用配置好的真实大模型（联网、消耗额度）
```

**标注集**（人工编写，逐条对照 `data/entities.json` 核对）

| 文件 | 规模 | 内容 |
|---|---|---|
| `data/eval/retrieval_eval.json` | 42 条（36 有答案 / 6 负样本） | 专名、别名、关系、属性、概念五类查询，逐条给出分级相关实体（3 = 直接答案，2 = 高度相关，1 = 弱相关） |
| `data/eval/qa_eval.json` | 24 条（21 可答 / 3 应拒答） | 期望引用实体 + 必答事实词；拒答样本要求系统明确说「没有」 |

**实测结果**（离线、本地检索式后端，`python scripts/evaluate.py`）

| 指标 | @1 | @3 | @5 |
|---|---|---|---|
| Hit（相关项是否出现在前 K 名） | 1.000 | 1.000 | 1.000 |
| Precision | 1.000 | 0.583 | 0.372 |
| Recall | 0.530 | 0.814 | 0.846 |
| nDCG（分级相关性下的排序质量） | 1.000 | 0.940 | 0.938 |

MRR 1.000 · MAP 0.819 · 负样本正确留空 0.667

按标签分组后差异很清楚（这正是分组的意义）：

| 标签 | 样本 | 命中 | 召回 | nDCG | 正确留空 |
|---|---|---|---|---|---|
| 专名 | 10 | 1.000 | 1.000 | 0.997 | — |
| 别名 | 10 | 1.000 | 0.783 | 0.924 | — |
| 关系 | 8 | 1.000 | 0.896 | 0.934 | — |
| 概念 | 7 | 1.000 | 0.635 | 0.869 | — |
| 属性 | 1 | 1.000 | 1.000 | 1.000 | — |
| 负样本 | 6 | — | — | — | 0.667 |
| 词面重叠 | 2 | — | — | — | 0.000 |

回答侧：引用覆盖 1.000 · 要点命中 1.000 · 可溯源 1.000 ·
作答率 1.000 · 拒答判断正确 1.000 · 未出现编造编号 1.000。

**这些数字怎么读**

- **@1 全对，但召回是瓶颈**：单一实体的问法都能把目标排到第 1 名；
  多实体问法（如「徽菜的代表菜品」有 7 个相关实体）在 top-5 里只能召回到一部分，
  所以 Recall@1 只有 0.530。这是检索条数（`QA_TOP_K`）与排序策略的取舍，不是 bug。
- **「关系」类召回 0.896 而非 1.000**：问「宏村属于哪个县」时，主体（宏村）稳居第 1，
  但作为答案的**对象实体**（黟县）不一定进前 5——关系确实进了索引，
  但对象实体自身的资料与查询词重合度不高。这是真实存在的改进空间，已如实记录。
- **两个「词面重叠」负样本会被误召回**：`区块链共识算法` 命中《算法统宗》、
  `Python 装饰器怎么用` 命中承志堂（其描述里有「装饰」）。这是词袋检索的固有局限，
  **不做剔除**——把它们单独打标签、单独统计，比藏起来更容易被看见。

**评估真的改进了产品**：首轮运行发现「徽商又被称为什么」这类问题答不出别名，
原因是别名参与匹配、却没有出现在送进后端的资料正文里。修正后要点命中率由 0.857 升到 1.000。

## 快速开始

### 1. 环境要求

- Python 3.10 以上（开发环境为 3.13）
- Windows / macOS / Linux 均可

### 2. 创建虚拟环境并安装依赖

Windows（PowerShell / CMD）：

```bat
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

macOS / Linux：

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

> 国内网络建议使用镜像：
> `pip install -r requirements.txt -i https://mirrors.aliyun.com/pypi/simple/`

### 3. 配置（可选）

问答功能在**未做任何配置**时即可使用——程序会自动降级到本地检索式后端（纯离线，无需 API Key）。

若要启用真实大模型生成回答：

```bat
copy .env.example .env
```

然后编辑 `.env`，任选其一填写：

- **自建 Dify**：填写 `DIFY_BASE_URL`、`DIFY_API_KEY`
- **OpenAI 兼容大模型**：填写 `LLM_BASE_URL`、`LLM_API_KEY`、`LLM_MODEL`

`.env` 已被 `.gitignore` 忽略，**不会进入版本库**。

后端生效顺序：`Dify` → `OpenAI 兼容大模型` → `本地检索式`。

### 4. 启动

```bat
streamlit run app.py
```

浏览器会自动打开 `http://localhost:8501`。

## 开发原则

1. 先检查现有文件与环境，再动手修改。
2. 模块化开发，每完成一个模块即运行并测试。
3. 不虚构 API、依赖或测试结果。
4. 所有按钮必须具备真实功能，不出现纯装饰按钮。
5. 文化事实必须标注可核查来源。
6. AI 回答严格基于检索到的资料；资料不足时明确说明，不编造。
7. 敏感配置只存于环境变量，绝不写入代码或版本库。
8. 所有模块均处理异常、空结果与加载状态。
