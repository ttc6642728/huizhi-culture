## 一、作品概述

徽知是一个把徽州文化整理成**结构化、可核查、可交互**知识的 Web 应用。它做四件事：

1. **浏览与检索** —— 96 个徽州文化实体按 11 个分类组织，支持中文关键词检索与分类筛选；
2. **看关系** —— 把 180 条实体关系建成知识图谱，可交互探索、聚焦实体、查询任意两实体的最短关联线路；
3. **基于资料提问** —— 用检索到的资料向 AI 提问，回答的每一处事实都带来源编号，可点击核查；
4. **看 AI 怎么想的** —— 一条六步智能体工作流把「问题解析 → 资料检索 → 依据资料作答 → 引用自我核查 → 纠正重试 → 输出归档」全程留痕，失败时明确写出停在哪一步。

### 一句话定位

> 不是「能聊徽州的聊天机器人」，而是一个**答案可溯源、过程可追踪、断网也能用**的文化知识平台。

### 完成情况一览（均为实测值，非计划值）

| 维度 | 实测 |
|---|---|
| 文化实体 | **96** 个（11 个分类） |
| 实体关系 | **180** 条（11 种关系类型） |
| 参考资料 | **33** 条（含 URL 与访问日期） |
| 孤立实体 | **0**（全部实体至少有一条关系，图谱连通） |
| 图片素材 | **15 张** Commons 自由授权图片（逐条署名）+ 1 张自备首页主视觉 |
| 代码规模 | 34 个源码模块 / 约 8 000 行；测试 16 个模块 / 约 3 400 行 |
| 自动化测试 | **390 个测试函数 / 437 个用例，全部通过**（约 34 秒，全程不联网） |
| 检索效果 | Hit@1/3/5 = **1.000**；Recall@5 = 0.846；nDCG@5 = 0.938；MRR = 1.000 |
| 回答效果（离线） | 引用覆盖率 / 要点命中率 / 可溯源率 = **1.000** |
| 回答效果（真实大模型） | 引用覆盖 0.976、要点命中 0.976（24 题 / 23 秒，DeepSeek） |
| 图谱产物 | 单文件 HTML 约 790 KB，**零外部资源引用**（断网可打开） |

## 二、立项背景与目标

### 2.1 为什么做这个

徽州文化（徽州一府六县：歙县、休宁、黟县、祁门、绩溪、婺源）是一个**关系极其密集**的文化对象：
古村落、徽派建筑、徽商、新安画派、新安理学、徽菜、非遗技艺、历史名人彼此交织，
用「词条列表」很难呈现它的结构——这正是知识图谱适合的场景。

同时，通用大模型在文化领域回答时存在两个真实风险：**来源不透明**、**容易编造细节**。
对文化类内容而言，「说得流畅但查无实据」比「不说」更有害。

### 2.2 要解决的四个问题

| 问题 | 本项目的做法 |
|---|---|
| 文化知识散落、看不出结构 | 建实体—关系数据集 + 知识图谱，结构可量化（中心性、聚类、路径） |
| AI 回答不可核查 | 回答严格基于检索资料，每处事实标编号，编号对应可点击来源；越界编号标红 |
| AI 过程是个黑盒 | 六步工作流逐步留痕：输入、输出、耗时、状态、明细全部可见 |
| 依赖外部服务就跑不起来 | 三层后端自动降级（Dify → 大模型 → 本地检索式），**断网也能完整演示** |

### 2.3 目标与范围

**做**：结构化数据 + 图谱 + 检索式问答 + 可追踪工作流 + 质量评估 + 完整的工程文档。

**不做**（明确划出边界）：不做用户系统与数据持久化；不做模型训练与微调；
不宣称自己具备大模型能力（本地检索式后端会明说「未经生成式改写」）；
不为了「看起来完整」而放空壳按钮或占位图。

## 三、需求分析

### 3.1 功能需求

| 编号 | 需求 | 落地位置 |
|---|---|---|
| F1 | 浏览文化实体，支持中文关键词检索与分类筛选 | 文化百科页 `src/ui/pages/explore.py` |
| F2 | 查看实体详情：结构化属性、正文、按方向分组的关联关系、可点击来源 | 实体详情页 `detail.py` |
| F3 | 交互式知识图谱：筛选、聚焦、点选高亮、缩放平移 | 知识图谱页 `graph.py` |
| F4 | 图谱结构分析：中心性、连通性、最短关联路径、聚类 | `src/graph/analysis.py` |
| F5 | 基于资料的 AI 问答，回答带来源引用 | 问答页 `ask.py` + `src/qa/` |
| F6 | 后端不可用时自动降级，且降级原因对用户可见 | `src/qa/engine.py` |
| F7 | 可追踪的多步智能体工作流，逐步留痕 | `src/agent/workflow.py` |
| F8 | 效果可量化：检索与回答的评估指标可复现 | `src/eval/` + `scripts/evaluate.py` |

### 3.2 非功能需求（这部分决定了实现方式）

| 编号 | 需求 | 为什么重要 | 如何保证 |
|---|---|---|---|
| N1 | **事实可核查** | 文化内容说错就是硬伤 | 实体与关系强制带 `source_ids`；11 类数据校验；关键事实写入测试断言 |
| N2 | **不编造** | 资料不足时「编一个」比「不知道」危害大 | 提示词禁止脱离资料；资料不足要求直说；域外问题测试断言必须拒答 |
| N3 | **离线可运行** | 答辩现场可能断网 | 图谱 HTML 内联全部资源且断言零外链；本地后端纯离线 |
| N4 | **不伪装** | 不能把本地检索包装成大模型 | 界面明确显示当前生效后端；本地答案开头声明未经生成式改写 |
| N5 | **无空壳** | 按钮必须真能用 | 所有按钮有真实功能；冒烟测试真实点击验证跳转 |
| N6 | **可复现** | 结论要能重现 | 布局固定随机种子；评估默认离线；测试不联网、不消耗额度 |
| N7 | **配置安全** | 密钥不得进版本库 | 只从 `.env` / 环境变量读取，`.env` 已 gitignore |

## 四、技术选型与环境约束

### 4.1 技术栈

| 层次 | 选型 | 版本 | 选择理由 |
|---|---|---|---|
| 应用框架 | Streamlit | 1.66.0 | 纯 Python 写完整 Web 应用，无需前后端分离；`AppTest` 可真实点击测试 |
| 图建模与分析 | NetworkX | 3.7 | 纯 Python，算法完备（中心性、连通分量、最短路、模块度聚类） |
| 图可视化 | PyVis | 0.3.2 | 产出**单文件 HTML**，可离线打开；不依赖 Graphviz 二进制 |
| 中文分词 | jieba | 0.42.1 | 轻量、离线、无需模型下载 |
| 检索 | 自实现 BM25 | — | 96 份资料规模下 BM25 足够且**完全可控、可解释**，便于调试与评估 |
| 数据 | JSON + 自实现校验 | — | 人类可读可改；校验在加载时强制，改错立刻报错 |
| 测试 | pytest | 9.1.1 | 参数化 + 覆盖率统计 + 与 Streamlit `AppTest` 配合 |
| 运行环境 | Python | 3.13.14 | — |

**为什么检索不用向量库**：本项目只有 96 份资料，BM25 的效果已由标注集实测（Hit@1 = 1.000），
引入向量模型会增加依赖体积与不可控性，且离线部署更麻烦。这是**有意识的取舍**，
其代价（概念类召回偏低）已在第八节如实记录。

### 4.2 环境约束（实测，直接影响了设计）

开发前先做了环境探测，三个结论改变了实现方案：

| 约束 | 实测结果 | 应对 |
|---|---|---|
| `pypi.org` 不可达，清华镜像对 pip 返回 403 | 阿里 / 腾讯 / 华为镜像正常 | 依赖安装走阿里云镜像（已写入文档） |
| `dify.ai` 云端不可达，本机无 Docker 自建 Dify | 无法真实联调 | 后端**可插拔 + 三层降级**，Dify 优先级最高但未配置时自动下探 |
| 本机对 Wikimedia 存在 **SNI 域名级阻断** | `commons`/`upload` 握手超时，`dumps` 正常 | 图片抓取改走**免费中转池** + 冷却退避轮换 |

这三条的共同教训：**先探测环境再设计**，否则会写出「在我机器上能跑」的方案。

## 五、总体设计

### 5.1 分层架构

```
                 app.py（Streamlit 入口：配置 / 主题 / 导航 / 路由）
                                  │
     ┌──────────────┬─────────────┼─────────────┬──────────────┐
     ▼              ▼             ▼             ▼              ▼
  ui/pages      ui/theme      src/data       src/graph      src/qa
  页面渲染      设计系统    加载·校验·查询   建模·分析·可视化  检索·问答
     │                                                        │
     │                          src/agent/workflow ◄──────────┘
     │                       可追踪的多步问答工作流
     └────────────────► src/eval（指标 / 标注集 / 评估运行）
```

**分层原则（关键）**：业务逻辑一律下沉，界面只做展示。因此数据层、图谱层、问答层、评估层
都能脱离 Streamlit 单独测试——这是 437 个用例里大部分可以**不启动界面**就跑完的前提。

| 层 | 依赖 | 说明 |
|---|---|---|
| `src/data` | — | JSON → 可查询对象，11 类校验，不含任何界面代码 |
| `src/graph` | `src/data` | 输出图对象、统计结果、HTML，不依赖 Streamlit |
| `src/qa` | `src/data` | 检索 + 可插拔后端 + 引用溯源，不直接操作界面 |
| `src/agent` | `src/qa` | 复用问答链路编排六步流程，产出步骤记录 |
| `src/eval` | `src/data` + `src/qa` | 指标纯函数 + 标注集 + 运行器，默认离线 |
| `src/ui` | 以上全部 | 只做展示与交互 |

### 5.2 数据模型

```
data/entities.json
  ├─ categories[]  { id, name, order, description }
  └─ entities[]    { id, name, category, aliases[], summary, description,
                     attributes{}, source_ids[], image? }

data/relations.json
  ├─ relation_types[] { id, name, inverse_name, description }
  └─ relations[]      { id, source, target, type, label, description?, source_ids[] }

data/sources.json
  └─ sources[]  { id, type, title, publisher, url, accessed, note }
```

**四条硬约束**（由 `src/data/loader.py::validate_dataset` 的 11 类检查强制）：

1. id 全局唯一；
2. 每条实体与每条关系**必须**带非空 `source_ids`，且引用的来源必须存在；
3. 关系方向固定 `source → target`；反向展示时用 `inverse_name`，不伪造方向；
4. **不允许孤立实体**——每个实体至少有一条关系（当前实测 0 个）。

### 5.3 界面设计系统

视觉取自徽州建筑本身：粉墙黛瓦 + 朱砂点缀。

| 令牌 | 值 | 用途 |
|---|---|---|
| `bg` / `bg_soft` / `surface` | `#FAF7F2` / `#F3EEE6` / `#FFFFFF` | 米白主背景 / 次级背景 / 卡片 |
| `ink` / `ink_soft` / `ink_mute` | `#22201C` / `#57534A` / `#8C867A` | 深墨主文字 / 次级 / 辅助 |
| `cinnabar` | `#B23A2F` | 朱砂点缀（选中、强调、引用编号） |
| `stone_dark` / `stone` / `stone_light` | `#3B3935` / `#7C786F` / `#D8D3C9` | 徽州建筑黑白灰 |

标题用衬线字体（Noto Serif SC → 宋体回退），正文无衬线，**全部系统字体、不依赖外链**。
11 个分类各有专色，定义在 `src/ui/theme.py` 并被图谱可视化复用（避免两处各写一份）。

### 6.3 P2 知识图谱（已完成）

**目标**：把数据变成图，让「关系」成为可看、可量、可交互的对象。

**产出**：`builder.py`（建模）/ `analysis.py`（分析）/ `visualize.py`（可视化）/
`runtime.py`（缓存适配）+ 图谱页 + `scripts/graph_report.py`。

**第一个关键决策：必须用 `MultiDiGraph`**

数据中存在同向平行边——「渐江 → 新安画派」同时有「创立」与「代表」两种关系。
`nx.DiGraph` 会**静默合并**同向平行边，导致关系数凭空少 1、图谱与源数据不一致。
这不是小瑕疵，是**数据失真**。改用 `MultiDiGraph` 后，测试直接从渲染产物里
解析 JS 数据载荷核对边数（180 条，与数据完全一致）。

代价与处理：连通性、最短路、聚类在无向简单视图上计算（折叠平行边）；
路径展示时若某段只有反向关系，标记 `reversed=True` 并渲染为 `A ←标签— B`，**不伪装成同向**。

**第二个关键决策：PyVis 的「离线自洽」不止是 `cdn_resources="in_line"`**

实测发现 pyvis 0.3.2 的模板会**无条件**（不受该参数控制）引入 Bootstrap 5 的 CDN 资源，
断网时图谱白屏。因此加了三步：内联 vis-network 资源 → `strip_external_resources()` 清洗 →
清洗后立即扫描，**若仍存在外部引用则直接抛错**（宁可报错，也不交付「看着能用、断网就白屏」的页面）。

**结构实测（P2 时点）**

| 指标 | 值 |
|---|---|
| 节点 / 边 | 90 / 150 |
| 连通分量 | 1（全部实体同属一个网络） |
| 网络直径 / 平均最短距离 | 6 / 2.939 |
| 图密度 | 0.0367 |
| 度数首位 | 徽州 41（**全是入边**） |
| 介数首位 | 徽州 0.7488 |
| 聚类 | 8 个（模块度优化，标注为探索性分析） |

**留了一个自己发现的问题**：「徽州」的 41 条关系全是入边、无出边。判断这是**真实的建模缺口**
而非数据噪声，记录进遗留，在 P3 解决。

**验证**：133 项用例通过；`graph_report.py` 输出「全部检查通过」；导出单文件 HTML 可独立打开。

### 6.5 P4 检索与 AI 问答（已完成）

**目标**：让平台能回答基于资料的问题，且**答案可溯源**。

**产出**：`src/qa/` 四个模块（errors / retriever / prompt / engine）+ 问答页。

**检索设计**：jieba 分词 + 停用词过滤 → BM25（k1=1.5，b=0.75）→ 精确命中加成 → 结果必带来源。
**关系叙述也进索引**（否则「胡适是哪里人」这类关系型问题答不出）。检索实测：

| 查询 | 首位结果 | 分数 |
|---|---|---|
| 宏村 | 宏村 | 13.78 |
| 马头墙有什么特点 | 马头墙 | 14.70 |
| 徽州三雕是什么 | 徽州三雕 | 11.78 |
| 胡适是哪里人 | 胡适 | 14.47 |

**三层后端自动降级**（最重要的一处设计）

| 优先级 | 后端 | 触发条件 | 特点 |
|---|---|---|---|
| 1 | `DifyBackend` | 配置了 `DIFY_BASE_URL` + `DIFY_API_KEY` | 满足「优先 Dify」的要求 |
| 2 | `LLMBackend` | 配置了 `LLM_BASE_URL` + `LLM_API_KEY` + `LLM_MODEL` | 任意 OpenAI 兼容接口 |
| 3 | `LocalRetrievalBackend` | 以上未配置，或 `QA_FORCE_LOCAL=true` | **纯离线**：BM25 + 抽取式答案 + 强制引用 |

**降级必须「可见」**：降级原因逐条展示在界面上，且绝**不把本地检索式包装成大模型能力**——
界面明确显示当前生效后端，本地答案开头声明「未经生成式改写」。

**引用溯源**：提示词要求模型用 `[n]` 标注每处事实的依据；引擎把解析出的编号与资料表比对，
**越界（编造）的编号单独记录并在界面标红**。

**真实大模型联调**（DeepSeek，非自动化测试）

```
问：徽商是什么？
→ 检索 5 条资料 → 作答 2.1s / 1707 tokens → 5 处引用全部对应到可点击来源

问：量子纠缠与超导体的关系是什么？
→ 模型回复：「本次检索到的资料与问题无关，无法回答。」（未编造）
```

**验证**：305 项用例通过，**全程不联网**——问答测试通过 `QA_FORCE_LOCAL=1` 强制本地后端，
后端失败分支用注入的假后端与假时钟覆盖，因此可离线复现、不消耗 API 额度。

### 6.6 P5 可追踪智能体工作流（已完成）

**目标**：把问答从「一次黑盒调用」变成「可追踪的多步流程」。

**六个步骤**（顺序、名称、职责以常量 `STEP_ORDER` / `STEP_TITLES` / `STEP_DUTIES` 定义，
**界面直接引用这些常量**，因此页面流程图不可能与代码执行顺序不一致）

| 步骤 | 做什么 | 中止条件 |
|---|---|---|
| 1 问题解析与实体锚定 | 判断提问类型；把问题里的实体名与别名锚定出来（长词优先） | 问题不合法 |
| 2 资料检索 | 放宽条件检索后把锚定实体提到首位；未出现时按名字补查一次 | 检索结果为空 |
| 3 依据资料作答 | **复用 P4 的同一套后端降级链** | 所有后端不可用 |
| 4 引用自我核查 | 6 项结构化核查，输出 pass / warn / fail 分级结论 | 不中止（如实上报） |
| 5 纠正重试 | 核查未通过且**仅一次**：带着具体缺陷重问 | 不中止（失败保留原答案） |
| 6 输出与归档 | 汇总答案、引用、核查结论与完整日志 | — |

```
P4：  question → retrieve → answer_from → QAResult        （一次调用，过程不可见）
P5：  question → intent → retrieve → answer_from → verify → [revise] → finalize
                  ↑ 每步记录 输入 / 输出 / 耗时 / 状态 / 明细
```

**两处刻意的克制**：

- **核查用程序判定，不用模型自评**——模型自己说「我引用正确了」没有约束力；
  实际的 6 项核查是结构化比对（有没有引用、编号是否越界、是否与检索资料对应等）。
- **纠正只做一次**——无限重试会掩盖问题且消耗额度；重试失败则保留原答案并如实记录。

**「关于项目」页**：可以**当场输入问题、当场运行**，看到六步时间线、核查表、逐步明细
（含降级说明、越界编号、纠正指令原文）与一份纯文本追踪日志（便于答辩演示）。

**验证**：340 项用例通过，覆盖步骤顺序、失败中止、日志完整性、核查与纠正重试。

## 七、关键实现要点

### 7.1 检索：BM25 + 精确命中加成 + 关系叙述入索引

纯 BM25 对短查询不稳定，因此对「查询词完整出现在名称/别名中」额外加成。
**关系叙述也进索引**：否则「胡适是哪里人」这类问题的答案（籍贯关系）根本不在任何实体的正文里。

### 7.2 三层后端降级，且降级可见

降级链在 `QAEngine` 内依次尝试，每次失败记录原因（区分「未配置」「不可用」「超时」「响应异常」），
最终把**逐条原因**展示给用户，而不是笼统一句「服务不可用」。

### 7.3 引用溯源与越界编号识别

提示词要求每处事实标 `[n]`；解析兼容半角与全角编号；引擎把编号与资料表比对，
**越界的（即模型编造的）编号单独记录并在界面标红**。这是「不编造」这条原则真正落地的地方。

### 7.4 MultiDiGraph 保真 + 离线自洽可视化

平行边不丢（关系数与数据一致）；产物零外部资源引用且由测试强制；布局随机种子固定（可复现）。

### 7.5 工作流：常量驱动 + 失败即中止

步骤顺序/名称/职责取自常量，界面引用同一份常量；任一步骤失败则余下步骤记「跳过」+ 中止原因，
整体状态四分：`completed` / `corrected` / `degraded` / `aborted`。

### 7.6 评估层：公式可手算、默认离线

指标是纯函数，测试用手算例子验证（不是「跑一遍不报错」）；评估默认固定本地后端，
因此**结果确定、任何人都能复现**。

3 条域外问题全部正确拒答，无编造编号。真实模型唯一没答全的一条是「马头墙的作用」缺「封火墙」。

### 8.4 真实运行验证（非自动化测试，如实记录）

应用实际启动：HTTP 200；六页渲染无异常；首页主视觉、百科页「有配图优先」、图谱节点无浮层均已人工确认。

## 九、开发中遇到的典型问题与解决

这一节记录**真实发生过**的问题，其中前四条是**产品/数据层面的真缺陷**，
后四条是实现与测试层面的坑。

| # | 问题 | 怎么发现的 | 处理 |
|---|---|---|---|
| 1 | **别名不可见**：别名参与分词匹配，却没进送后端的资料正文，「徽商又被称为什么」必然答不出 | P6 评估首轮，要点命中只有 0.857 | 别名进资料正文 → 要点命中 **0.857 → 1.000** |
| 2 | **「没配」被当成「出错」**：真实运行时每次都被判「完成但存在问题」，因为核查把「Dify：未配置」算成问题 | P6 真实 DeepSeek 运行 | 新增 `is_config_skip` / `split_degradations`，核查项改为「未发生后端故障」；跳过仍**可见**但不再误报 |
| 3 | **图片图文不符**（最严重）：「渐江」是广东江河航拍、「徽州牌坊」是白云寺院门、「徽州祠堂」是无锡惠山祠堂 | 交付测试先抓到一张缺作者，顺此**逐张目视核查实际图片内容** | 剔除 4 条（20 → 15 张）；把关抽成纯函数；带地域的建筑类型名加地域必含词；新增「Commons 已登记作者」门槛；12 项新用例钉住 |
| 4 | **「徽州」是纯汇点**（41 条全是入边） | P2 结构分析 | 判断为真实建模缺口，P3 补一府六县概念层 → 度数 47（出 6 / 入 41），并固化为测试 |
| 5 | 单线程假 HTTP 服务器挂死：keep-alive 下 `shutdown()` 永久阻塞 | 写 Dify HTTP 测试时测试被 SIGTERM | 改 `ThreadingHTTPServer` + 守护线程 |
| 6 | 代理环境下断言不成立：连接失败被代理回成 502 而非抛 `ConnectionError` | Dify HTTP 测试 | 改为断言真正的不变量（必须翻译成项目自己的异常），异常映射单独做确定性测试 |
| 7 | 快照把全局样式表算进页面，每页都是同一份主题类名 | 界面快照测试 | 只统计页面内容，排除 `<style>` 块 |
| 8 | 测试 `_body()` 只收集 `markdown`，漏掉 `st.caption`，导致断言说明文字时假失败 | 交付后调整第二轮 | 同时收集 markdown 与 caption |

**另外两处「把关」的双向校准**：既挡住不该进的（第 3 条），
也要检查有没有把该进的错挡——复核时发现 `huiju` 因候选描述写「徽戏」而必含词只有「徽剧」被误挡，已补入。

### 10.2 这个作品的四个特点

1. **答案可溯源，且「不编造」是被代码强制的**——不是提示词里写一句「请诚实」，
   而是引用编号与资料表程序化比对，越界编号会被抓出来标红。
2. **过程可追踪**——六步工作流逐步留痕，核查用程序判定而非模型自评，失败写明停在哪一步。
3. **断网也能完整演示**——三层后端降级到纯本地；图谱 HTML 零外部依赖且有测试强制。
   「降级」这件事本身对用户可见，且从不把本地检索包装成大模型。
4. **效果有数，且短板公开**——评估建立在人工标注集上、指标可手算核对、默认离线可复现；
   概念类召回 0.635 这类短板写在文档里，不藏在漂亮的总分背后。

### 10.3 开发方法上的三条经验

1. **先探测环境，再设计方案**。pypi 不可达、Dify 不可达、Wikimedia 被 SNI 阻断——
   这三条如果事后才发现，P3 与 P4 都要返工。
2. **把事实固化成测试**。文化数据里的关键事实（遗产编号、非遗批次、牌坊数量）一旦被误改，
   靠人检查是记不住的，靠测试是每次都检查。
3. **评估先定标准，再跑结果**。标注先写、评估后跑，不拿结果反推标准——
   否则指标只会越来越好看，而不能揭示问题。

## 十一、不足与后续改进

如实登记，不做美化。

| 项目 | 现状 | 原因与下一步 |
|---|---|---|
| **概念类检索召回 0.635** | 当前最明显的短板 | 词袋检索对概念类问题天然吃力。下一步：引入**关系三元组级检索单元**，或加一层查询扩展 |
